# bunwa — deferred work

What is not done, with enough context to act on it later without re-deriving
why. Roadmap items live in docs/08; this file is for what was noticed in
passing and deliberately left.

Finished work is not recorded here. Git history is the record of what was done.


## 1. The consent challenge is never sent, and no reply is ever parsed

Blocks stage-1 exit criterion 2.

`POST /v1/devices/claim` answers 202 when a number belongs to another project.
It creates the consent row and its challenge token, and stops there.
`DeviceStore.respondToConsent` exists, is tested, and has no caller outside
those tests. Nothing sends the WhatsApp message and nothing watches for a
reply. The response carries `consentDelivery: "not_implemented"` so a client
can branch on it rather than parse prose.

A second project cannot obtain a number a first project holds, except by an
operator approving it directly.

To close: somewhere to send from — the holding project's own device — plus an
inbound rule that recognises the reply and calls respondToConsent with the
token. The engine consumer already receives inbound messages and the rules
engine already matches them; what is missing is the flow between them, and a
decision about what happens when the holder never replies.


## 2. Re-measure the blind window against Baileys

The 203-second gap between a silent disconnect and the engine admitting it is a
*gowa* measurement (docs/12). It is why a send is confirmed by a delivery ack
rather than by the engine accepting it, and why `sweepUnacked` exists.

A real device has now paired, so this is finally measurable. It is the oldest
unverified assumption in the project and the delivery design rests on it.


## 3. Run tenant regex matching in a terminable worker

Static analysis of a regex cannot be complete, and JavaScript cannot pre-empt a
running match. The budget therefore *detects* a slow pattern rather than
preventing it: one pathological regex occupies the event loop on every event
that reaches it, not once.

In place: RE2-only syntax, nested quantifiers refused at any depth, quantified
alternations refused when branches overlap, subject truncated to 4KB, a
per-match time budget whose breaches are logged.

Missing: the ability to kill a match in progress, which needs it running
somewhere killable — a Worker, with the match sent across and a hard timeout on
the host side.

Four review passes each found a gap in the static analysis, each narrower than
the last. That is convergence, and also evidence the approach is hard to get
exhaustively right. The worker makes all of the above defence-in-depth rather
than the primary guard.


## 4. A rule that blows its match budget is never switched off

`evaluate()` reports `timedOut` rule ids, the consumer logs a warning, and the
rule runs again on the next event and blows its budget again, for ever.
Patterns are RE2-compiled so there is no catastrophic backtracking, but a
tenant can leave a permanently slow rule in place and every inbound message
pays for it.

To close: count consecutive breaches per rule id, disable the rule through
RuleStore once it passes a threshold, reset on any clean evaluation, and emit
an event so the tenant learns their rule was switched off rather than
discovering it silently stopped matching.


## 5. Close the DNS rebinding window

Webhook and media URLs are tenant-supplied, so every outbound request goes to
an address a customer controls. The resolved address is validated immediately
before each request and refused if any answer is blocked (private, loopback,
link-local, cloud metadata).

The gap: Bun's fetch cannot bind a connection to an already-validated IP while
preserving the Host header and TLS SNI. A resolver that returns a public
address to the check and a private one to the connect is still followed.

Closing it needs an HTTP client over `Bun.connect` — connect to the pinned
address, set Host and SNI from the original URL. Security-critical code to own,
which is why it is hardening work rather than something to improvise.


## 6. The delivery queue is per environment; the design says per virtual device

docs/05 specifies "actions → delivery queue (per virtual device)" and docs/03
repeats the per-device scope. `deliveries` has no virtual-device column,
`DeliveryStore.enqueue` takes an environmentId, and the worker caps in-flight
work per environment. Two virtual devices in one environment share a queue.

A webhook endpoint that is slow or failing for one device therefore delays
events for every other device in the same environment — the head-of-line
blocking per-device queueing exists to prevent. Not a regression; no version
ever queued per device.

To close: add virtual_device_id to deliveries (nullable, since some events are
environment-scoped), migrate, key the worker's cap on it, fall back to the
environment for rows without one. The CodeRabbit path instruction for
src/delivery/** already states the requirement, so it will keep being reported
until the schema matches it.


## 7. A super-admin key that is not also a project key

The operator key is minted into `default/production`, so it is simultaneously
the instance admin and a tenant credential able to send messages as that
project. `default/production` is created on every boot for this reason alone.

The constraint is one column: `api_keys.environment_id` is NOT NULL with a
foreign key to `environments`.

  (a) Make it nullable and let a key with instance scopes have no tenant. Every
      route derives its tenant from the credential — the invariant the auth
      design rests on, stated in src/auth/middleware.ts — so
      `AuthContext.projectId` becomes nullable and ~15 handlers must answer
      "what if there is no tenant". Most answer 403.
  (b) A separate `operator_keys` table with its own resolver and middleware.
      Leaves `api_keys` intact, at the cost of two auth paths that can drift —
      and stream tickets reference `api_keys.id`, so an operator opening the
      event stream needs that FK relaxed anyway.

Recommend (a). Until then the bootstrap project is badged "instance" in the
projects list so it does not read as a tenant someone created.


## 8. Operator cannot act on a tenant's devices

To claim a number or read a conversation for a tenant you sign in with that
tenant's key. Clean boundary, and it means debugging a tenant requires their
credential — which an operator can mint, but only by creating a key that then
exists.

Alternative: let an operator select a project and act within it. That is a
tenant-scoping change on every project route, with scope coming from a
parameter rather than only from the credential — exactly what the current
design refuses to do. Wants deliberate thought, not a flag.


## 9. Warn at startup when the operator key is behind the current scope set

Adding a scope leaves every existing key short of it, and the symptom is a
screen that 403s or a menu item that silently disappears. `key:list` reports
missing scopes, but only if someone runs it. A line at boot — "the operator key
is missing manage:projects; run bun run key:grant <prefix>" — would have caught
both occurrences in one session before either was noticed as a bug.


## 10. The claim flow beyond the first fix

The claim screen now watches the binding it started, says it is waiting while
the code is outstanding, and announces the device and moves to Devices when it
connects.

The rest of the flow has not been looked at. Worth walking end to end with a
real phone and writing down each place the screen cannot answer the question
the operator has, rather than guessing from the code.


## 11. Console gaps

  - No ProjectsPage component test. The store and the routes are tested; the
    page is not.
  - Environments cannot be created from the console. The admin API supports it;
    the UI only lists them, so a project created in the console has no
    environment until one is added over HTTP — and a project with no
    environment cannot issue keys, which the UI says but does not let you fix.
  - Deleting or suspending a project is not exposed anywhere.

## Open question: one unexplained test failure

A full `bun test` run once reported 1 failure where every run before and after
reported none. The output carried no `(fail)` line and named no test. Not
reproduced since, across many full runs and every CI run.

Kept because "it went away" and "it is rare" are the same observation, and the
next person to see one failure in a green suite should know it has happened
before rather than assume they broke it.

If it recurs: capture the whole run output rather than the tail, since the
identifying line is what was missing. Bun's runner shares one process across
files, so the first suspects are the module-level singletons the console stores
use and the env-var save/restore in the logger and setup suites.
